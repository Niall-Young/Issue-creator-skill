# Agent-ready Issue handoff templates

Choose exactly one template based on the primary deliverable. Preserve the headings so Issues remain scannable across projects. Replace the guidance with task-specific facts; do not leave instructional placeholders in the published Issue.

Every acceptance criterion must describe an observable result. Use `待确认` only for a non-blocking unknown and explain how the implementing agent can resolve it. If an unknown changes the goal, scope, or acceptance criteria, ask the user before publishing.

## Feature

Title: `[Feature] <用结果描述功能>`

```markdown
## 任务目标

<完成后用户或系统获得的具体能力>

## 背景与现状

<为什么需要该能力；当前仓库已经具备什么、缺少什么>

## 用户场景与期望行为

<谁在什么情况下执行什么操作，系统应如何响应>

## 仓库上下文

- 相关路径/模块：`<path>`
- 当前入口或接口：`<symbol or command>`
- 已确认事实：<基于代码、配置、测试或文档的事实>

## 任务范围

- <必须实现的行为或接口变化>

## 不在范围内

- <本任务明确不处理的相邻事项>

## 验收标准

- [ ] <可观察的成功结果>
- [ ] <关键边界或兼容行为>

## 验证方式

- `<测试、构建或检查命令>`
- <必要的人工验证步骤>

## 约束与注意事项

- <兼容性、安全性或不能破坏的现有行为>

## 参考信息

- <相关 Issue、PR、文档或用户材料；没有则写“无”>
```

## Bug

Title: `[Bug] <描述可观察的错误行为>`

```markdown
## 任务目标

<修复后应恢复的正确行为>

## 背景与现状

<问题影响、出现位置和已知范围>

## 实际结果

<当前可观察到的错误行为或原始错误信息>

## 预期结果

<同一条件下应出现的行为>

## 复现条件

1. <已验证的步骤或最小触发条件>

> 无法验证的步骤必须标为 `待确认`，不得补写成事实。

## 仓库上下文

- 相关路径/模块：`<path>`
- 相关测试或入口：`<path, symbol, or command>`
- 已有证据：<日志、失败测试、代码路径或用户报告>

## 任务范围

- <需要修复的行为>
- <需要补充的回归测试>

## 不在范围内

- <不属于本次修复的重构或扩展>

## 验收标准

- [ ] <原问题不再出现>
- [ ] <回归测试能在修复前失败、修复后通过，或给出等价验证>
- [ ] <相关既有行为保持正常>

## 验证方式

- `<针对性测试命令>`
- `<必要的完整检查命令>`

## 约束与注意事项

- <兼容性、数据安全或潜在回归点>

## 参考信息

- <相关 Issue、PR、日志或用户材料；没有则写“无”>
```

## Refactor

Title: `[Refactor] <描述要改善的结构或维护结果>`

```markdown
## 任务目标

<重构完成后的结构、维护性或工程结果>

## 背景与现状

<当前结构造成的具体成本、重复、耦合或维护问题>

## 仓库上下文

- 目标路径/模块：`<path>`
- 相关入口或依赖：`<symbol or path>`
- 当前结构：<基于代码确认的简述>

## 必须保持的不变量

- <对外行为、接口、数据格式或兼容性要求>

## 目标结构

- <期望形成的职责边界或工程状态，不强行规定未验证的实现细节>

## 任务范围

- <需要完成的结构调整>

## 不在范围内

- <不顺带改变的产品行为或无关模块>

## 验收标准

- [ ] <结构结果可由代码或工具检查>
- [ ] <必须保持的行为由测试证明未变化>
- [ ] <旧路径、重复实现或临时兼容层按要求处理>

## 验证方式

- `<测试、构建、类型检查或静态检查命令>`

## 约束与注意事项

- <迁移顺序、兼容窗口或风险点>

## 参考信息

- <相关 Issue、PR、设计文档；没有则写“无”>
```

## Research

Title: `[Research] <描述需要回答的问题或决策>`

```markdown
## 调研目标

<需要回答的核心问题，以及答案将支持的后续决策>

## 背景与现状

<为什么现在需要调研；已有信息和未知点>

## 待回答问题

- <必须形成结论的问题>

## 仓库上下文

- 相关路径/模块：`<path>`
- 已有实现或约束：<基于仓库确认的事实>

## 调研范围

- <需要检查的代码、方案、数据或外部一手资料>

## 不在范围内

- <本 Issue 不直接实施的改动或不比较的方向>

## 证据要求

- <结论需要引用的代码位置、实验结果、基准或权威来源>
- <必须区分已验证事实、推断和建议>

## 预期交付物

- <报告、决策记录、可复现实验或后续 Issue 建议>

## 验收标准

- [ ] <每个待回答问题都有证据支持的结论>
- [ ] <权衡、风险和未决问题清楚列出>
- [ ] <给出可执行的下一步建议>

## 验证方式

- `<复现实验或检查命令；不适用时说明人工复核方式>`

## 约束与注意事项

- <时间范围、版本、平台或不能触碰的环境>

## 参考信息

- <相关 Issue、PR、文档或来源；没有则写“无”>
```
